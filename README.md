# 音乐年龄测试（中文版 · 网易云 + QQ 音乐 + 酷我音乐）

**在线体验：[netease-music-age.onrender.com](https://netease-music-age.onrender.com/)** — 打开就能测，无需安装，粘贴网易云 / QQ 音乐主页链接或酷我用户 ID 即可。

输入一个网易云音乐主页链接，勾选 TA 的任意公开歌单（「我喜欢的音乐」、自建歌单、收藏歌单都可以），根据这些歌单里的全部歌曲，算出 TA 的**音乐年龄**。适合不把歌都放在「喜欢」里、而是分类整理成多个歌单的人。

现已支持 **QQ 音乐**（网站顶部可切换平台）：填 QQ 号、QQ 音乐个人主页链接，或任意公开歌单链接，算法相同。QQ 音乐走其网页端公开只读接口（匿名可读，前提是对方主页/歌单公开）；歌曲本身不带年份，按专辑逐张补查发行日期；「我喜欢」在 QQ 音乐需要登录才能读取，暂不支持——可计算的是公开自建歌单与歌单链接，也没有「听歌排行视角」。

还支持**酷我音乐**：填酷我用户 ID 或任意公开歌单链接。列歌单走酷我老服务按 uid 取公开歌单（**含「我喜欢听」**），取歌走 www 接口、逐曲自带所属专辑的发行日期（其中 `1970-01-01` 是酷我的「日期未知」哨兵值，按缺年份处理）；令牌 cookie 由后端现取现算（名字会被酷我轮换，不能硬编码）。酷我网页端没有主页链接模型，入口只有用户 ID 和歌单链接。

其他主流平台（Spotify、Apple Music、YouTube Music、酷狗音乐）经逐一调研和实测，暂时都无法以同样方式接入，具体原因见下文「[支持的平台与不支持的原因](#支持的平台与不支持的原因)」。

玩法来自日本站「音楽数珠つなぎ」的 30 MUSIC CHALLENGE：假设每首歌都是在它发行的那一年、你 17 岁时听到的，那么——

> **单曲音乐年龄 = 当前年份 − 发行年份 + 17**，全部歌曲取平均，就是你的音乐年龄。

比如一首 1969 年的歌：1969 年时 17 岁的人，现在 74 岁。歌单越老，音乐年龄越大。作为参照，原站公布的用户平均音乐年龄是 28 岁。

## 算法

很简单，一共三步：

1. **取年份**：对歌单里的每一首歌，取其所属专辑的发行年份（网易云接口的 `album.publishTime`）。
2. **逐首换算**：假设你是在这首歌发行的那一年、17 岁时听到它的，那么“这首歌的音乐年龄”就是那位 17 岁听众现在的年龄：
   `单曲音乐年龄 = 当前年份 − 发行年份 + 17`
3. **取平均**：把全部歌曲的单曲音乐年龄做算术平均、四舍五入取整，就是这个人的音乐年龄。

细节说明：

- 没有发行年份的歌曲（如部分新歌单曲）不参与计算，数量会在结果中单独注明；
- 不做加权——每首歌权重相同，算的是“歌单品味的平均年代”，不是“实际收听频次”；
- 选了多个歌单时先合并**去重**：同一首歌在几个歌单里重复出现，只算一次；
- **重制版校正**：歌所在专辑若是重制版、再版或精选集，专辑发行年份会晚于歌曲原版年份、把结果算小（实测一个 5,000 多首的歌单里这类歌占约一成，单首后延可达 20–40 年）。对这类歌，会另外搜索同歌手同名歌曲的最早版本，用最早年份替换——但只有早 3 年以上才替换，避免一两年的噪声；结果里会注明校正了多少首、不校正会算成多少岁。疑似判定有两种：①歌名或专辑名带 Remaster、Deluxe、精选、Hits 等标记；②同一批歌里已经有同名同歌手的更早版本（早 3 年以上）——这首多半来自精选集或再版，即使专辑名不带任何标记（例如精选集《Warheads On Foreheads》里的 Tornado Of Souls，计入 2019 年、原版 1990 年）也能抓到。校正走的是批量流水线而不是逐首查：先按歌名去重分组；同一批歌里已有干净原版的组直接用批内年份校正、免搜索（实测约 1/5 的组）；其余组并发搜索只拿候选，再把候选按专辑去重、合并成大批量的详情请求（80 组实测详情请求从约 90 次降到 1 次），并带专辑年份缓存。实测一个 5,368 首的歌单全程从约 15 分钟降到约 4 分钟；个别搜不到原版的歌保留专辑年份。残余偏差：专辑名不带标记、且歌单里没有更早同名版本的精选集歌曲仍可能漏掉，所以校正后的结果是「明显减小偏差」，不是理论上的完全消除。
- **中位数**：结果同时给出中位数音乐年龄（每首歌的单曲年龄排序后取中间值）。平均值容易被极端值拉动——比如一首 1936 年的歌单曲年龄 107 岁，在小歌单里能把平均值抬高好几岁；中位数几乎不受影响。两者差得越多，说明歌单里越有极端老歌或新歌。

结果里还有一组「听歌排行视角」（对方公开了听歌排行时才有）：

- **历史最爱**：只拿听歌排行里播放量最高的 100 首歌（`user_record` 累计榜）按同一公式测算——代表 TA 真正反复在听的歌；
- **最近一周**：只拿最近一周的听歌排行测算，再和歌单算出的音乐年龄对比，差值在 2 岁以上时给出结论：最近在往新歌走（变年轻）还是在回头听老歌（变老）。

## 在线体验（网站版）

本项目自带一个完整的网站：打开页面 → 粘贴网易云主页链接 → 勾选要计入的歌单（默认勾选「我喜欢的音乐」+ 全部自建歌单，收藏的别人歌单会标注创建者、默认不勾选）→ 自动拉取并算出音乐年龄（平均值和中位数一起给），结果卡下方还附「听歌排行视角」（历史最爱 Top100、最近一周，及变年轻/变老的结论），带进度条，手机上也能用。结果页可以一键**生成分享图 PNG**（大字年龄、年代分布、Top 歌手、最老的歌），方便发到社交平台；还可以接着玩**「手选挑战」**（原版 30 MUSIC CHALLENGE 玩法）：从这次算过的歌里（歌单 + 听歌排行）选手选再算一次，挑战长度可选 **10 / 20 / 30 首**（默认 20），有两种模式——**命题向导**照原站结构做了 30 个命题（分日常与心情 / 标题与特征 / 回忆与喜好三类，命题文案本站自拟；短版从中均匀抽题、末题仍是「你自己的主题曲」），一题一首逐题作答，带进度格、已答清单、实时平均预览，答满后逐题列出答案回顾；**自由选**模式提供「最老的 / 最新的 / 历史最爱」三个参考歌单一键预选。候选里没有的歌（比如流媒体上找不到的宝藏歌）可以**手动添加**，自己填歌名、音乐人和发行年份；挑战结果同样能**生成分享图 PNG**（含全部选歌清单，向导模式带命题）。全量歌单是真实品味，手选是你心中的代表作，两个分数会直接对比。正式站点就是顶部的在线体验地址（Render 免费实例闲置后会休眠，下次打开需等几十秒唤醒）。


本地预览同理，执行 `npm start` 后打开 http://localhost:3000 。

网站结构：

- `server.js` — 零额外依赖的 Node 后端，只负责取数：网易云部分解析主页/短链接、返回用户的全部歌单列表（按创建者区分自建/收藏）与任意歌单的全量 trackIds、返回听歌排行、批量查询歌曲发行年份、为重制/再版歌曲查询原版年份（带缓存与失败重试）；QQ 音乐部分走网页端公开只读接口列自建歌单、取歌单歌曲并按专辑补发行年份；酷我音乐部分按用户 ID 列公开歌单、分页取歌（逐曲自带发行年份），令牌现取现算；
- `public/` — 前端页面（输入框、歌单多选、进度条、结果卡），跨歌单去重与音乐年龄计算在浏览器端完成；
- `music-age.js` — 命令行版（见下节），同样支持多歌单，与网站共用同一套算法。

## 快速开始（命令行版）

需要 Node.js 18+。

```bash
npm install
node music-age.js "https://music.163.com/user/home?id=1"
```

也可以直接传用户 ID：

```bash
node music-age.js 1
```

默认只算「我喜欢的音乐」。把歌分类放在不同歌单里的人，用参数选择歌单：

```bash
node music-age.js 1 --list            # 先列出全部公开歌单（含各自的 ID）
node music-age.js 1 --all             # 「我喜欢的音乐」+ 全部自建歌单
node music-age.js 1 --ids=123,456     # 只算指定的几个歌单（ID 见 --list）
node music-age.js --qq 123456789      # QQ 音乐：QQ 号（算全部公开自建歌单）
node music-age.js --qq "https://y.qq.com/n/ryqq_v2/playlist/9801330057"   # QQ 音乐：直接按一个公开歌单算
node music-age.js --qq 123456789 --list                                    # QQ 音乐：先列出公开自建歌单
node music-age.js --kuwo 413836986                                         # 酷我音乐：用户 ID（算全部公开歌单，含「我喜欢听」）
node music-age.js --kuwo "https://www.kuwo.cn/playlist_detail/2410926933"  # 酷我音乐：直接按一个公开歌单算
node music-age.js --kuwo 413836986 --list                                  # 酷我音乐：先列出公开歌单
```

运行后会输出：

- 音乐年龄（平均值）和对应的“世代”标签（如：千禧一代的耳朵、泡沫经济世代的耳朵），以及中位数音乐年龄
- 参与计算的歌曲数（以及因缺发行年份被剔除的数量）
- 歌单里最老和最新的一首歌
- 年代分布（60 年代 / 70 年代 / …）和出现最多的歌手 Top 5

同时在 `output/` 目录生成一份可分享的 HTML 结果卡（`music-age-<用户ID>.html`）和一份 JSON 原始结果。

## 工作原理

以下以网易云为例（QQ 音乐、酷我的数据流见各自的小节说明，算法与去重规则相同）。网易云的数据层不重复造轮子，直接使用开源项目 [Binaryify/NeteaseCloudMusicApi](https://github.com/Binaryify/NeteaseCloudMusicApi)（网易云音乐 Node.js API 的事实标准）：

1. 从主页链接解析用户 ID，分页取用户资料和**全部公开歌单**；
2. 给歌单分类：「我喜欢的音乐」看 `specialType === 5`；自建/收藏看**创建者**——`creator.userId` 等于本人是自建，否则是收藏的别人歌单（注意：歌单的 `subscribed` 字段在匿名请求时恒为 null，不能用它区分）；
3. 按使用者的选择（网页勾选，或命令行的 `--all` / `--ids`）确定要计入的歌单；
4. 用 `playlist_detail` 拿到每个歌单的**全量 trackIds**——千首级歌单也不会被截断（不足时再用 `playlist_track_all` 分页补齐），合并后跨歌单去重；
5. 按 500 首一批调用 `song_detail`，取每首歌的专辑发行时间（`album.publishTime`），逐首换算后取平均；
6. 对疑似重制/再版/精选专辑的歌（关键词标记，或同批歌单里已有更早的同名同歌手版本），用 `cloudsearch` 搜同歌手同名歌曲、取最早版本的发行年份做校正（规则见上文「重制版校正」；实现上是批量流水线：内部可直判的组免搜索、搜索只拿候选 ID、候选按专辑去重后合并成 500 一批的 `song_detail` 大请求、专辑年份全程缓存）；
7. 排行视角另调 `user_record`（type=1 最近一周 / type=0 累计），取榜单歌曲重复第 5、6 步。

全程**免登录、只读公开数据**，不保存任何账号信息。

## 支持的平台与不支持的原因

本项目接入一个平台的前提是同时满足三条：①能凭主页链接/用户 ID/歌单链接**匿名**读取公开歌单（不登录任何人的账号）；②能拿到歌单的**全部**歌曲；③每首歌能得到可信的**发行年份**。目前的平台支持情况如下。

### 已支持

| 平台 | 入口 | 发行年份来源 | 主要限制 |
| --- | --- | --- | --- |
| 网易云音乐 | 主页链接 / 用户 ID | 歌曲所属专辑的 `album.publishTime`，另有重制版校正 | 歌单需公开；听歌排行视角取决于对方的排行可见性 |
| QQ 音乐 | QQ 号 / 主页链接 / 歌单链接 | 歌曲本身不带年份，按专辑逐张补查发行日期 | 「我喜欢」需要登录才能读取，不支持；没有听歌排行视角 |
| 酷我音乐 | 用户 ID / 歌单链接 | 逐曲自带所属专辑的发行日期（`releaseDate`） | 网页端没有主页链接，只能填用户 ID；令牌需后端现取现算 |

### 未支持

**Spotify——平台政策关门（不是技术问题）。** 2026 年 2 月起，新建的开发者应用被官方删除了「按用户 ID 读资料 / 歌单列表」的端点（`GET /users/{id}`、`GET /users/{id}/playlists`），歌单曲目也只返回本人拥有或协作的歌单；开发模式还要求应用所有者持有 Premium、每个应用最多 5 名白名单用户。想恢复「贴链接读任意公开歌单」只能申请 Extended Quota，门槛是合法注册企业 + 25 万月活，个人项目不可达。它的发行年份字段（专辑 `release_date`）本身没有问题，卡住的是权限。

**Apple Music——没有匿名入口。** 官方 API 的一切请求都要带 Developer Token，必须用付费的 Apple Developer Program 账号（$99/年）里的 MusicKit 密钥签发；平台没有「他人主页」的概念，不存在按用户链接列出其公开歌单的端点，读取用户自己的曲库还需要该用户本人登录授权（Music User Token）。目录端点最多能读「已公开分享的单个歌单」。免费的 iTunes Search API 只能按歌名查目录歌曲、补发行年份，碰不到任何歌单和用户。

**YouTube Music——没有可靠的逐曲发行年份。** 非官方库 ytmusicapi 本身成熟活跃，匿名读公开歌单也没问题，但它返回的每首歌只有标题、歌手、专辑名等字段，**没有年份**；年份只存在于专辑级（打开专辑页才有），只能按专辑逐个补查。更麻烦的是歌单里大量曲目是普通视频 / 用户上传内容，根本没有正规专辑可查，这部分永远拿不到年份——算出的音乐年龄会建立在残缺样本上，所以没有接入。另：用户的「喜欢的歌曲」列表永远是私密的，匿名拿不到。

**酷狗音乐——没有可匿名枚举他人歌单的接口。** 酷狗唯一的「用户歌单」接口必须带歌单主人**本人的登录 token**，传别人的用户 ID 调不通，产品上也没有网易云 / QQ 那种可分享、可凭 ID 打开的公开主页模型。新版歌单（`global_collection_id`）的全量歌曲虽然有一个免登录的网关接口，但必须补齐整套 Android 签名 + 设备注册（`dfid`）才让调，还会触发验证码风控，自维护成本远高于其他平台；老式数字 ID 歌单可以走零签名的老接口并按专辑补 `publishtime`，但只覆盖老歌单。综合考虑，暂未接入。

## 注意事项

- **要计入的歌单需要设为公开**。如果对方把歌单设为隐私，匿名接口拿不到，程序会给出提示。
- **听歌排行视角取决于对方的排行可见性**。对方在网易云 App 里把听歌排行设为私密时，这两项会跳过（主结果不受影响）。
- 部分歌曲（尤其是新歌单曲）的专辑没有发行时间，这类歌曲会被剔除并在结果里注明数量。
- 若所在网络环境需要代理，程序会自动读取环境变量 `https_proxy` / `HTTPS_PROXY`。
